# 플레이북 — 인프라 진단 MCP 서버

> **목표를 먼저 문장으로 고정합니다.**
> *"장애 원인을 계층별 지표로 좁혀가는 내 방법론을 Claude가 쓸 수 있는 도구로 만들었다."*
>
> 이 문장이 이력서에 들어갈 것이고, 만드는 내내 이 문장에서 벗어나지 않는지 확인합니다.

---

## 왜 이걸 만드는가

### 갭 두 개를 한 번에 메웁니다

| 갭 | 현재 상태 | 이 프로젝트로 |
| --- | --- | --- |
| **MCP 미경험** | 커넥터를 연결해 쓴 수준. 서버 구현 없음 | 서버를 직접 설계·구현 |
| **AI 효과 검증** (렌트리 자격요건 9) | Agent 4종은 만들었으나 **정확도를 측정한 기록 없음** | 평가셋으로 도구 선택 정확도 측정 |

### 왜 하필 "인프라 진단"인가

다른 주제(노트 검색, 문서 요약)로 만들면 **누구나 만드는 MCP 서버**가 됩니다. 인프라 진단은 다릅니다.

- 지용님의 **최강 카드(계층별 지표 대조로 원인 추적)를 도구로 옮긴 것**입니다
- DB CPU 편차 사례에서 한 일 — 스냅샷이 모순되자 샘플링으로 전환하고, 성격이 다른 계층의 비율이 균일한 걸 포착한 것 — 이걸 **함수로 만들면 재사용 가능한 자산**이 됩니다
- 면접에서 "AI 써봤어요?"가 아니라 **"본인 전문성을 AI가 쓸 수 있게 만들었네요"**로 대화가 바뀝니다

## 만들 것 — 도구 5개

읽기 전용입니다. 쓰기(재시작·스케일·삭제)는 **넣지 않습니다.** 이유는 아래 설계 판단 ①에.

| # | 도구 | 하는 일 | 난이도 |
| --- | --- | --- | --- |
| 1 | `query_metrics` | PromQL 실행, 시계열 요약 반환 | 낮음 |
| 2 | `search_logs` | Loki 라벨 셀렉터 + 필터, 상위 N건 | 낮음 |
| 3 | `get_workload_state` | K8s Deployment/Pod 상태·재시작 횟수·최근 이벤트 | 중간 |
| 4 | ⭐ `compare_layers` | **두 대상의 계층별 지표를 대조해 비율 반환** | 높음 |
| 5 | ⭐ `list_ruled_out` | 증상별로 **이미 배제한 가설과 근거** 조회 | 중간 |

### 4번과 5번이 이 프로젝트의 전부입니다

1~3번은 이미 공개된 MCP 서버가 많습니다. 그것만 만들면 차별점이 없습니다.

**`compare_layers`** — 두 호스트(또는 파드)를 받아 CPU·메모리·디스크 I/O·네트워크·컨텍스트 스위치를 같은 시간창으로 뽑고 **비율을 계산해 반환**합니다. 비율이 계층마다 다르면 워크로드 문제, **모든 계층에서 균일하면 실행 환경 문제**입니다. DB CPU 편차 사례에서 하신 판단을 그대로 코드화한 것입니다.

**`list_ruled_out`** — "이 증상에서 이미 배제한 가설이 무엇이고 근거가 무엇인가"를 반환합니다. 지용님이 실무에서 이미 하시는 일(배제한 가설을 근거와 함께 문서화)을 모델이 조회하게 만드는 것입니다. **모델이 같은 가설을 반복 제안하는 걸 막습니다.**

> 5번은 YAML 파일 몇 개로 시작해도 됩니다. 벡터DB 필요 없습니다. 증상 → 배제 목록 매핑이면 충분합니다.

## 단계별 구현

### 0단계 — 붙일 대상 준비 (이미 있음)

사이드 프로젝트의 K3s + Prometheus + Grafana + Loki 스택을 그대로 씁니다. **새로 만들 필요 없습니다.**

⚠️ **사내 시스템에 절대 붙이지 마세요.** 개인 GitHub에 올릴 코드입니다. 엔드포인트·자산명·IP가 커밋되면 되돌릴 수 없습니다.

### 1단계 — 도구 1개로 끝까지 (반나절)

`query_metrics` 하나만 만들고 **Claude Code에 실제로 붙여서 답을 받는 것**까지 갑니다. 도구 5개를 다 만들고 나서 연결하면 어디가 깨졌는지 모릅니다.

```
[성공 기준] Claude에게 "노드 CPU 사용률 지금 어때?"라고 물었을 때
           도구가 호출되고 숫자가 담긴 답이 온다
```

### 2단계 — 도구 확장 (하루)

`search_logs` → `get_workload_state` 순서. 각각 붙일 때마다 **이전 도구가 여전히 선택되는지** 확인합니다. 도구가 늘면 모델이 엉뚱한 걸 고르기 시작합니다.

### 3단계 — 차별화 도구 (하루)

`compare_layers`와 `list_ruled_out`. 여기에 시간을 쓰세요. 1~3번은 재료이고 **이 둘이 결과물**입니다.

### 4단계 — 평가 (반나절) ⭐ 이걸 빼면 프로젝트 가치가 절반입니다

질의 10~15개를 고정해두고 **어떤 도구를 골랐는지, 답이 맞았는지** 기록합니다.

```
질의                                    기대 도구            결과
"왜 이 파드가 계속 재시작하지?"          get_workload_state   ✓
"A와 B 서버 성능 차이 원인이 뭐야?"      compare_layers       ✓
"이 증상 전에 뭘 확인했었지?"            list_ruled_out       ✗ → search_logs 선택
```

**틀린 케이스가 나오면 도구 설명(docstring)을 고칩니다.** 이 과정이 곧 *"AI 도구의 효과를 검증했다"*의 실체입니다. 렌트리 자격요건 9번이 정확히 이걸 묻습니다.

## 설계 판단 — 이력서에 쓸 부분

### ① 읽기 전용으로 시작한 것

재시작·스케일·삭제 도구를 넣지 않았습니다. **모델이 틀리면 그대로 사고**이기 때문입니다.

자원 회수 파이프라인에서 `Dry-run`을 기본값으로 둔 것과 **같은 판단**입니다. 자동화의 목적은 사람을 빼는 게 아니라 사람이 판단할 지점을 남기는 것 — 이 서사가 이어집니다.

> 쓰기가 필요하면 **제안만 반환**하세요. `suggest_action`이 명령어 문자열을 돌려주고 실행은 사람이 합니다.

### ② 응답 크기를 제한한 것

프롬프트 컨텍스트는 유한합니다. 로그 전문을 반환하면 한 번 호출에 컨텍스트가 다 찹니다.

- 상위 N건 + 집계 요약만 반환
- 시계열은 원본 포인트가 아니라 **min/max/p95/평균 + 변화 구간**
- 반환 상한을 코드에 못박기

### ③ 실패를 빈 결과로 반환하지 않은 것

조회 실패를 `[]`로 돌려주면 모델이 **"정상입니다"로 오독**합니다. 명시적 에러를 반환합니다.

**"틀린 답보다 모른다는 답"** — FastAPI 시스템에서 동점이면 미매칭으로 남긴 것과 같은 원칙입니다. 이 일관성이 이력서에서 강합니다.

### ④ 자격증명을 서버가 소유한 것

토큰은 환경변수로 서버가 들고 있고 **모델에는 노출하지 않습니다.** 모델은 도구를 호출할 뿐 자격증명을 보지 못합니다.

### ⑤ 쿼리 상한과 타임아웃

무제한 range PromQL이 들어오면 Prometheus가 죽습니다. 최대 조회 구간과 타임아웃을 서버가 강제합니다.

## 이력서 반영 문장 (완성 후)

**Side Project 섹션에 추가:**

> ### 인프라 진단 MCP 서버
> **(개인 프로젝트 | 2026.09)**
>
> 장애 원인을 계층별 지표로 좁혀가는 진단 절차를 Claude가 호출할 수 있는 도구로 구현했습니다.
>
> - **[차별화 도구]** 두 대상의 계층별 지표를 같은 시간창으로 대조해 비율을 반환하는 `compare_layers` — **비율이 계층마다 다르면 워크로드, 균일하면 실행 환경 문제**라는 실무 판단 기준을 함수로 구현
> - **[반복 제안 차단]** 증상별로 이미 배제한 가설과 근거를 조회하는 도구를 두어, 모델이 같은 가설을 다시 제안하지 않도록 구성
> - **[읽기 전용 설계]** 재시작·스케일 등 쓰기 도구는 제외 — 모델이 틀리면 그대로 사고이므로 **제안만 반환하고 실행은 사람이** 하도록 경계를 명확히
> - **[검증]** 진단 질의 N개에 대해 도구 선택 정확도를 측정하고, 오선택 케이스는 도구 설명을 수정해 개선

**Tech Stack `AI` 줄 갱신:**

> 사내 LLM Gateway 연동, Context Injection, 목적별 Agent 분리 설계, **MCP 서버 구현**, Claude Code

**면접 답변:**

> 사내 게이트웨이가 툴 콜링을 지원하지 않아 업무에서는 Context Injection으로 우회했습니다. 다만 툴 콜링이 가능한 환경이면 어떻게 설계할지 궁금해서 개인적으로 MCP 서버를 만들어봤고, 제가 장애를 볼 때 쓰는 계층 대조 절차를 도구로 옮겼습니다. 만들면서 알게 된 건 **도구 설명이 곧 프롬프트라서 개수가 늘수록 선택 정확도가 떨어진다**는 것이었고, 그래서 도구를 5개로 제한했습니다.

# 다른 프로젝트 후보 — ROI 순

## 1위. DORA 지표 측정 파이프라인 ⭐⭐⭐ (사내 · 다른 개발팀을 위한 서비스)

**지금 가장 큰 구멍을 실측 데이터로 메웁니다.**

현재 배포 리드타임 수치(2h→15m)는 사이드 프로젝트뿐이고, **실무 배포 지표가 없습니다.** JD 대부분이 이걸 묻습니다.

### 무엇을

사내 GitHub Actions 워크플로 이벤트를 수집해 팀별로 네 지표를 계산합니다.

| 지표 | 계산 |
| --- | --- |
| **배포 빈도** | 성공한 배포 워크플로 수 / 기간 |
| **변경 리드타임** | 커밋 시각 → 배포 완료 시각 |
| **변경 실패율** | 롤백·핫픽스 배포 / 전체 배포 |
| **MTTR** | 실패 배포 → 다음 성공 배포 |

### 왜 지용님이 하기 좋은가

- **이미 만든 FastAPI 시스템에 붙입니다.** 새 시스템이 아니라 확장입니다
- 데이터 수집·정규화·판정은 **이미 하신 일과 같은 구조**입니다
- 변경 실패율 판정에서 또 **"근거를 무엇으로 볼 것인가"** 문제가 나옵니다 — 롤백 태그? 핫픽스 브랜치? 재배포 간격? 편향 방향을 비교하는 방법론을 그대로 재사용
- **다른 개발팀이 자기 지표를 직접 보는 서비스**가 됩니다. 셀프서비스 서사가 한 겹 더 두꺼워집니다

### 얻는 이력서 문장

> 팀별 배포 빈도·리드타임·변경 실패율·MTTR을 자동 수집해 **N개 팀이 직접 조회**하도록 구성. 리드타임 중앙값 X분 → Y분

⚠️ 조직 지표를 공개하는 일이라 **팀 리더와 합의 먼저** 하세요. "누가 느린지 줄 세우기"로 읽히면 반발이 큽니다. **팀 단위 익명화 + 추이 중심**으로 설계하시길 권합니다.

## 2위. OpenTelemetry 트레이스 ⭐⭐ (가장 저렴·빠름)

**로그·메트릭·트레이스 삼각형에서 트레이스만 비어 있습니다.**

렌트리 자격요건 6번, 대부분의 SRE JD가 이 세 단어를 함께 씁니다. 지금은 둘만 있습니다.

### 무엇을

이미 있는 FastAPI 시스템에 OpenTelemetry 계측을 넣고, 외부 API 호출 5종(변경 티켓·CMDB·문서·관제·메신저)의 구간을 스팬으로 남깁니다.

### 왜 효과가 큰가

- **주말 하루면 됩니다.** 새로 만들 게 없고 계측만 붙입니다
- 이미 `prometheus-fastapi-instrumentator`로 RPS·에러율·p95를 보고 계십니다. **"p95가 왜 느린가"에 답할 수 있게** 되는 게 트레이스입니다
- 실제로 쓸모가 있습니다 — 5종 API 중 어디가 느린지 지금은 모르실 겁니다
- Promtail이 EOL이고 **Grafana Alloy가 메트릭·로그·트레이스를 한 프로세스에서 다룬다**는 걸 이미 알고 계십니다. 그 이야기와 이어집니다

### 얻는 이력서 문장

> FastAPI 서비스에 OpenTelemetry 계측을 적용해 **외부 시스템 5종 연동 구간을 스팬으로 분리** → p95 지연의 원인 구간을 특정

## 3위. MCP 서버 ⭐⭐ (위 플레이북)

차별화가 가장 크지만, 1·2위보다 실무 연결이 약합니다. **개인 프로젝트**로 남습니다.

---

## 4위. AWS 실습 + SAA ⭐⭐⭐ (갭은 최대, 비용·시간 듬)

**10개 JD 중 7개가 AWS 갭입니다.** 크기로는 1위지만 주말 몇 번으로 안 끝납니다.

### 최소 경로

Terraform으로 VPC → EKS → ALB → 애플리케이션 배포까지 한 번 관통하고 **`terraform destroy`로 지웁니다.** 온프레미스에서 하신 것과 같은 구조를 클라우드 이름으로 바꿔 세워보는 게 목적입니다.

⚠️ **EKS는 컨트롤 플레인만으로도 시간당 과금**됩니다. 실습 후 반드시 파기하고, 예산 알림을 먼저 걸어두세요.

### 얻는 것

*"AWS 프로덕션 운영은 없습니다"* 뒤에 붙일 문장이 생깁니다 — *"다만 Terraform으로 VPC부터 EKS까지 직접 세워봤고, 온프레미스에서 하던 것과 무엇이 같고 다른지는 확인했습니다."*

SAA는 그 다음입니다. **자격증보다 세워본 경험이 먼저**입니다.

---

## 5위. External Secrets Operator ⭐ (작지만 정확한 갭 메우기)

시크릿 관리가 `.env`·K8s Secret 수준에서 멈춰 있습니다. 사이드 프로젝트 K3s에 ESO를 붙이면 *"조직 표준은 못 만들어봤지만 도구는 안다"*까지 갑니다. **반나절**이면 됩니다.

---

## 우선순위 정리

```
당장 (주말 1~2회)      2위 OpenTelemetry  →  5위 ESO
실무에서 (합의 필요)    1위 DORA 파이프라인          ← 가장 큰 실익
개인 프로젝트          3위 MCP 서버                 ← 가장 큰 차별화
장기 (한 달+)          4위 AWS + SAA               ← 가장 큰 갭
```

**하나만 고르라면 1위(DORA)입니다.** 실무 지표가 생기고, 다른 팀을 위한 서비스이고, 이미 만드신 시스템의 확장이라 새로 배울 게 적습니다.

**주말에 당장 시작하고 싶으시면 2위(OpenTelemetry)입니다.** 투입 대비 효과가 제일 좋습니다.

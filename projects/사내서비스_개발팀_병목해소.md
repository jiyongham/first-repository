# 개발팀 병목 해소 사내 서비스 — 후보와 선택 기준

> **인프라팀이 게이트인 지점을 찾아 게이트를 없애는 일입니다.**
> 렌트리 JD 첫 줄이 *"개발자가 인프라 담당자의 개입 없이 애플리케이션을 배포하고, 상태를 확인하고, 문제를 추적할 수 있는 내부 플랫폼"*입니다. 이건 그 JD의 답안을 실무로 만드는 작업입니다.

---

## 0단계. 만들기 전에 병목을 측정하세요 ⭐

**어떤 걸 만들지 감으로 고르면 안 됩니다.** 지용님이 IaC 파이프라인에서 하셨던 것 — *"자원이 방치되고 있다는 건 모두 알았지만 '유휴'의 정의가 없었다"* — 와 같은 상황입니다.

### 이미 데이터를 갖고 계십니다

입사 초기에 만드신 **JIRA 티켓 대시보드**에 답이 있습니다. 접수부터 처리까지의 흐름을 이미 보고 계시니, 여기에 **유형 분류**만 얹으면 됩니다.

```
티켓 유형별로 뽑을 것

  건수        — 무엇이 가장 자주 오는가
  처리 시간   — 무엇이 가장 오래 걸리는가
  대기 시간   — 접수 후 착수까지 (← 개발자가 체감하는 병목)
  반복률      — 같은 팀이 같은 요청을 몇 번 하는가
```

⭐ **대기 시간이 핵심 지표입니다.** 처리에 10분 걸려도 착수까지 이틀이면 개발자는 이틀을 기다린 것입니다. 자동화 효과가 가장 큰 건 **처리가 짧은데 대기가 긴 유형**입니다.

### 이게 왜 중요한가

- **baseline이 생깁니다.** 만든 뒤 "티켓 N% 감소"를 말할 수 있습니다. 지금 이력서에 부족한 게 정확히 이런 실무 지표입니다
- **감이 아니라 데이터로 골랐다**는 서사가 됩니다. 이력서에서 이 한 줄이 결과 수치만큼 강합니다
- 조직 설득이 쉬워집니다 — *"이 유형이 전체의 30%이고 평균 대기가 이틀입니다"*

> 아래 후보들은 제 추정입니다. **실제 티켓 분포가 다르면 순위도 달라집니다.** 측정을 먼저 하세요.

## 후보 1. 서비스 상태 셀프 진단 페이지 ⭐⭐⭐

**"내 서비스 왜 느려요?"를 개발팀이 스스로 확인**

### 왜 병목인가

개발팀은 서버 접속 권한도, 관제 시스템 계정도 없는 경우가 많습니다. 그래서 이상하면 인프라팀에 물어봅니다. 인프라팀은 **매번 같은 화면 몇 개를 열어 확인해주고 있습니다.**

### 무엇을

서비스명 하나를 넣으면 흩어진 것을 한 화면에 모읍니다.

| 영역 | 소스 | 보여줄 것 |
| --- | --- | --- |
| 리소스 | Prometheus / Polestar | CPU·메모리·디스크 추이, 임계치 근접 여부 |
| 애플리케이션 | Prometheus | RPS·에러율·p95 |
| 로그 | Loki | 최근 에러 상위 N건 (전문 아님) |
| 변경 | JIRA | 최근 변경 티켓 — **"어제 뭐 바뀌었나"** |
| 알람 | 관제 | 최근 발생 알람과 현재 상태 |
| 자산 | CMDB | 구성 요소 목록, 담당자 |

⭐ **"최근 변경"이 이 페이지의 핵심입니다.** 장애 원인의 상당수가 변경입니다. 개발자가 *"어제 인프라 쪽에서 뭐 건드렸나?"*를 스스로 확인할 수 있으면 문의 자체가 줄어듭니다.

### 가진 재료

**전부 있습니다.** Prometheus·Loki·Polestar·JIRA·CMDB 연동을 이미 하셨고, FastAPI 시스템에 화면을 하나 더 붙이는 구조입니다.

### 리스크

낮습니다. **읽기 전용**이고, 보여줄 범위를 자산 소유 팀으로 제한하면 됩니다.

### 이력서 문장

> 개발팀이 자기 서비스의 리소스·에러율·최근 변경·알람을 한 화면에서 확인하는 **셀프 진단 페이지**를 구축 — 인프라팀 경유 문의를 X% 감소

### JD 정합성

렌트리 주요업무 1번의 **"상태를 확인하고, 문제를 추적할 수 있는"**에 문장 그대로 대응됩니다.

## 후보 2. 신규 서비스 온보딩 골든 패스 ⭐⭐⭐

**새 서비스 하나 띄울 때마다 반복되는 등록 절차를 한 번에**

### 왜 병목인가

새 서비스가 뜨면 등록해야 할 곳이 흩어져 있습니다 — 관제 대상, 백업 정책, DR 티어, 자산 관리, 알람 수신자, 로그 수집. **개발팀은 뭘 해야 하는지 모르고, 인프라팀은 매번 같은 안내를 반복합니다.**

그리고 누락되면 **사고가 난 뒤에 발견됩니다.** "모니터링이 안 걸려 있었네요"가 그것입니다.

### 무엇을

서비스 정보를 한 번 입력하면 필요한 등록을 자동 수행하고, **자동화가 안 되는 항목은 체크리스트로** 남깁니다.

```
입력: 서비스명 · 담당자 · 티어 · 구성 자산

자동:  CMDB 등록 → 관제 대상 추가 → 알람 수신자 설정
       → 로그 수집 라벨 → 백업 정책 매핑 → DR 티어 지정

수동:  자동화 불가 항목을 티켓으로 생성하고 진척 추적
```

⭐ **티어를 고르면 백업·DR·알람 수준이 따라오게** 만드는 게 핵심입니다. 지용님이 만든 **티어별 DR 표준**이 여기서 실행 가능한 형태가 됩니다. 문서로 있던 표준이 코드가 되는 것입니다.

### 가진 재료

- 티어별 DR 표준 — **직접 제정하셨습니다**
- 3-2-1 백업 전략, KISA 체크리스트
- CMDB·관제 API 연동 경험

### 리스크

중간. 자동 등록이 잘못되면 잘못된 정책이 걸립니다. → **`Dry-run` 기본값**을 여기서도 씁니다. 등록 계획을 먼저 보여주고 승인 후 실행.

### 이력서 문장

> 신규 서비스 온보딩 시 관제·백업·DR·자산 등록을 **티어 선택 한 번으로 일괄 적용**하는 골든 패스를 구축 — 문서로만 존재하던 티어별 표준을 실행 가능한 형태로 전환. 등록 누락 X건 → 0건

### 왜 강한가

**"표준을 만든 사람"에서 "표준이 자동으로 적용되게 만든 사람"으로 올라갑니다.** 이력서 전체 서사(규칙을 사람의 주의에 맡기지 않는다)와 정확히 이어집니다.

## 후보 3. 연결성 진단 도구 ⭐⭐

**"A에서 B로 통신이 안 돼요"를 개발자가 스스로 확인**

### 왜 병목인가

인프라팀 티켓에서 비중이 큰 유형입니다. 그런데 원인은 대부분 몇 가지로 정해져 있습니다 — 방화벽 미오픈, 잘못된 포트, 서비스 미기동, 라우팅, DNS.

**개발자는 어느 구간에서 막혔는지 볼 방법이 없어서** 무조건 인프라팀에 묻습니다.

### 무엇을

출발지·목적지·포트를 넣으면 구간별로 어디서 끊겼는지 반환합니다.

```
DNS 해석        ✓ 10.x.x.x
라우팅 경로     ✓ 도달 가능
방화벽 정책     ✗ 정책 없음  ← 여기
대상 리스닝     -
```

### 가진 재료

네트워크·커널 영역은 **지용님의 최강점**입니다. 다만 **방화벽 정책 조회 API가 있는지**가 관건입니다. 없으면 범위를 라우팅·리스닝·DNS까지로 줄이면 됩니다 — 그것만으로도 "인프라 문제인지 앱 문제인지"는 갈립니다.

### 리스크

⚠️ **보안 검토가 필요합니다.** 방화벽 정책 조회는 그 자체가 정찰 정보가 될 수 있습니다. 자기 팀 자산 관련 구간만 보이도록 제한하고, **조회 이력을 남기세요.**

### 이력서 문장

> 개발팀이 출발지·목적지·포트로 통신 차단 구간을 스스로 확인하는 진단 도구를 개발 — 연결성 문의 티켓 X% 감소

## 후보 4. 셀프서비스 자원 신청 ⭐

**VM·스토리지 신청을 티켓 대기 없이**

### 왜 후순위인가

병목 크기는 가장 클 수 있습니다. Terraform과 Prism API를 이미 다루시니 **기술적으로는 가장 가깝습니다.**

그런데 **조직 문제가 기술보다 큽니다.**

- 쿼터와 승인 권한을 누가 정하는가
- 과금·원가 배분은 어떻게 되는가
- 잘못 생성되면 회수는 누가 하는가
- 보안 검토를 건너뛰는 경로가 되지 않는가

기술은 주말에 되지만 **합의는 몇 달 걸립니다.** 먼저 시작하면 만들어놓고 못 여는 상황이 됩니다.

### 그래도 하려면

**전체를 열지 말고 한 종류만** 여세요. 예를 들어 개발 환경 VM만, 정해진 스펙 3종 중 선택, 만료일 필수 지정, 만료 시 자동 회수. 범위를 좁히면 합의도 쉽습니다.

여기서도 **`Dry-run` 원칙**이 그대로 적용됩니다 — 생성 계획을 보여주고 승인 후 실행.

## 추천

### 하나만 고른다면 — 후보 2 (온보딩 골든 패스)

이유가 셋입니다.

1. **지용님이 만든 표준이 재료입니다.** 티어별 DR 표준, 백업 전략, KISA 체크리스트를 이미 제정하셨습니다. 남이 만든 걸 자동화하는 게 아니라 **본인 것을 실행 가능하게 만드는 일**입니다
2. **누락이 사고로 이어지는 영역**이라 가치가 명확합니다. "모니터링이 안 걸려 있었다"는 설득이 필요 없는 문제입니다
3. 이력서 서사가 한 단계 올라갑니다 — 표준을 **만든** 사람에서, 표준이 **자동으로 적용되게 만든** 사람으로

### 가장 빨리 효과를 보려면 — 후보 1 (셀프 진단 페이지)

재료가 전부 있고, 읽기 전용이라 리스크가 낮고, 기존 FastAPI 시스템에 화면 하나 붙이는 구조입니다. **주말 2~3회**면 첫 버전이 나옵니다.

### 조합이 가장 좋습니다

```
후보 1 (진단 페이지)  ←  개발팀이 스스로 본다
      +
후보 2 (온보딩)       ←  처음부터 제대로 등록된다
```

**등록이 제대로 되어야 진단 페이지가 보여줄 게 있습니다.** 둘은 사실 한 시스템의 앞뒤입니다.

## 만들 때 지킬 원칙 — 이미 갖고 계신 것들

새로 만들 필요 없습니다. 기존 원칙을 그대로 적용하면 됩니다.

| 원칙 | 어디서 왔나 | 여기서 어떻게 |
| --- | --- | --- |
| **`Dry-run` 기본값** | 자원 회수 파이프라인 | 자동 등록·생성은 계획을 먼저 보여주고 승인 후 실행 |
| **틀린 답보다 모른다는 답** | FastAPI 판정 로직 | 데이터 조회 실패를 "정상"으로 표시하지 말 것. **명시적으로 "확인 불가"** |
| **판정 근거의 편향 확인** | 세 소스 비교 | 상태 판정에 여러 소스를 쓸 때 어느 쪽으로 치우치는지 먼저 확인 |
| **읽기 전용부터** | — | 1단계는 조회만. 쓰기는 합의가 끝난 뒤 |
| **민감 정보 분리** | `.env` 관리 | 자산 식별자·엔드포인트는 코드에 두지 않기 |

## 조직 관련 주의

- ⚠️ **"인프라팀 일을 개발팀에 떠넘긴다"로 읽히면 실패합니다.** 프레이밍이 중요합니다 — *"기다리지 않아도 되게"*이지 *"직접 하세요"*가 아닙니다
- ⚠️ 파일럿 팀을 **한 팀만** 정해서 시작하세요. 전사 공개는 그다음입니다. 초기 오답이 전사에 퍼지면 신뢰 회복이 어렵습니다
- ⚠️ 티켓 감소를 성과로 말할 때, **"인프라팀이 일을 덜 한다"가 아니라 "개발팀이 덜 기다린다"**로 표현하세요. 같은 숫자여도 받아들여지는 방식이 다릅니다
- 0단계 측정 결과를 먼저 공유하면 설득이 훨씬 쉽습니다

# ⭐ 후보 0. VM 솔루션 설치 현황 셀프 조회 (2026-09 추가)

> **본인 아이디어. 앞의 어떤 후보보다 낫습니다.**
> 온보딩 골든 패스(후보 2)는 **신규만** 커버하지만, 이건 **이미 돌고 있는 4,000대 전체**를 커버합니다.

## 왜 이게 제일 나은가

### ① 판정 근거 문제가 그대로 반복됩니다 ⭐⭐⭐

**"설치됨"을 무엇으로 볼 것인가** — FastAPI 시스템에서 이미 푼 문제와 **구조가 완전히 같습니다.**

| 판정 소스 | 편향 | 이유 |
| --- | --- | --- |
| CMDB 등록 여부 | **과대계상** | 등록만 하고 실제 미설치일 수 있음 |
| 관제 heartbeat | **과소계상** | 네트워크·방화벽 문제로 끊기면 미설치로 오판 |
| 에이전트 콘솔의 클라이언트 목록 | — | **에이전트가 스스로 보고한 것** = 실동작 증명 |
| VM 내부 프로세스·패키지 직접 조회 | 가장 정확 | 접근 권한 필요, 대규모에서 느림 |

에이전트 콘솔을 1차 근거로 두고 **CMDB를 교차검증**으로 쓰는 게 자연스럽습니다.

> ⭐ **이력서 관점에서 이게 핵심입니다.** 완료 판정에서 세 소스의 편향을 비교한 사례가 **두 번째로 생깁니다.** 한 번이면 우연이지만 두 번이면 방법론입니다. "이 사람은 숫자를 만들기 전에 숫자의 편향부터 확인한다"가 증명됩니다.

### ② "설치됨"과 "정상 동작"은 다릅니다

설치돼 있어도 서비스가 죽어 있거나, 백업이 걸려 있어도 **최근 성공 이력이 없으면** 의미가 없습니다.

```
백신      설치 ✓  +  패턴 버전 날짜
백업      설정 ✓  +  마지막 성공 시각        ← 이게 진짜 정보
관제      등록 ✓  +  마지막 수집 시각
로그 수집 설정 ✓  +  최근 수신 여부
```

**상태를 4단계로** 두세요. 3단계로 하면 조회 실패가 "미설치"로 둔갑합니다.

| 상태 | 의미 |
| --- | --- |
| 정상 | 설치 + 최근 보고 있음 |
| ⚠️ 주의 | 설치됐으나 오래 미보고 |
| ✗ 미설치 | 근거 다수가 부재 확인 |
| **? 확인 불가** | **조회 실패 — 정상도 미설치도 아님** |

네 번째가 없으면 **"틀린 답보다 모른다는 답"** 원칙이 깨집니다.

### ③ 누락이 곧 사고인 영역입니다

백업 에이전트 미설치는 **사고가 난 뒤에** 발견됩니다. 백신 미설치, 관제 미등록도 마찬가지입니다. 설득이 필요 없는 문제라 조직 승인이 쉽습니다.

ISMS 심사 항목이자 KISA 체크리스트 항목이기도 합니다 — **이미 하신 일과 직결**됩니다.

### ④ 온보딩 골든 패스의 baseline이 됩니다

```
후보 0 (설치 현황)  →  누락을 발견하고 커버리지를 측정
      ↓
후보 2 (온보딩)     →  신규에서 누락이 재발하지 않게
      ↓
후보 0 재측정        →  온보딩의 효과가 숫자로 증명됨
```

**후보 0을 먼저 만들어야** 후보 2의 성과를 말할 수 있습니다. 순서가 중요합니다.

우선순위: **백업 → 관제 → 백신 → 로그 수집**

## 리스크 — 이건 반드시 지키세요

⚠️ **에이전트 미설치 목록은 그 자체가 공격 표적 목록입니다.**

- 자기 팀 소유 자산만 조회되게 제한
- **조회 이력을 남길 것**
- 전사 미설치 목록 일괄 조회·내보내기는 **인프라팀·보안팀만**
- 화면에 IP와 호스트명을 함께 노출할 필요가 있는지 검토

⚠️ **"그럼 설치도 우리가 하나요?"** — 조회 전용임을 명확히 하고, 미설치 항목은 **설치 요청 티켓 생성 버튼**으로 연결하세요. 개발팀이 확인하고, 실행은 인프라팀이 합니다.

## 이력서 문장

> ### VM 보안·백업 솔루션 설치 현황 셀프 조회 서비스
>
> - **[개요]** 개발팀이 자기 자산의 백업·관제·백신·로그 수집 적용 여부를 직접 확인하도록 구성 — 인프라팀 경유 확인 요청을 대체
> - **[판정 신뢰성]** 설치 판정 근거의 **편향 방향**을 비교 — CMDB 등록은 과대계상, 관제 heartbeat는 네트워크 단절 시 과소계상 → **에이전트 콘솔 보고를 1차 근거로 채택**하고 CMDB를 교차검증에 사용
> - **[설치와 동작 분리]** 설치 여부만으로는 무의미하므로 **마지막 백업 성공 시각·패턴 버전·최근 수집 시각**을 함께 표시
> - **[확인 불가 상태 분리]** 조회 실패를 미설치로 표시하지 않도록 상태를 4단계로 구분
> - **[성과]** 백업 미적용 자산 N건 선제 발견, 컴플라이언스 커버리지 X% → Y%

**"컴플라이언스 커버리지 X% → Y%"는 KISA 72% → 93%과 같은 종류의 숫자**입니다. 이력서에서 잘 작동하는 형태이고, 실제로 측정 가능합니다.

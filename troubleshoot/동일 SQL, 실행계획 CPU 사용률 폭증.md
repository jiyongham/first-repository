### A. 이력서 압축 버전 (3~4줄)

> **POS 서비스 DB 서버 CPU 사용률 이상 원인 규명 및 개선 (Oracle 19c / RHEL 7.6 / Nutanix AHV)**
> 
> - 동일 구성 서버 2대 간 CPU 사용률 15% 차이 발생, 피크 시 88% 도달. 실행계획·바인드 변수·THP·커널 파라미터 등 11개 가설을 AWR·ASH·sar 지표로 순차 검증·배제
> - OS·DB·시스템 데몬 전 계층에서 CPU 소모 비율이 1.14~1.24배로 **균일하게** 나타나는 점에 착안, 소프트웨어가 아닌 CPU 실행 성능 문제로 가설 전환
> - openssl 벤치마크로 하드웨어 처리량 12% 열세를 실측 입증 → 가상화 노드 CPU 경합으로 특정, 여유 노드 이관 후 **CPU 사용률 71% → 59% (12%p 개선)**

### B. 경력기술서 상세 버전

#### POS 서비스 DB 서버 CPU 이상 원인 분석 (2026.09)

**환경**  
Oracle 19c Single Instance, RHEL 7.6, 4 vCPU / 32GB VM 2대, Nutanix AHV, POS 거래 처리 서비스

**문제 상황**  
동일 SQL_ID·실행계획·PLAN_HASH를 사용하는데 서버 간 CPU 사용률이 지속적으로 차이. 한쪽이 주간 내내 상대 서버보다 10%p 이상 높고 피크 시 88%까지 상승. 서비스 영향 우려로 원인 규명 요청.

**분석 과정**

1. **DB 계층 검증** — GV$SQL·AWR(`DBA_HIST_SQLSTAT`)로 실행당 CPU·Logical Read·처리 건수 비교. 실행계획 변경, 결과 건수 차이, 바인드 민감도를 우선 배제.
2. **OS 계층 검증** — THP 활성화 차이를 발견해 비활성화했으나 개선 없음. HugePages가 이미 명시적으로 구성(7.3GB)되어 SGA가 영향권 밖이었음을 확인. `sysctl` 전수 diff로 설정 드리프트를 찾았으나 TCP 소켓 사용량이 상한 대비 2% 수준이라 무관 판정.
3. **측정 방법론 전환** — `v$session`·`top -n1`·`systemd-cgtop` 등 스냅샷 지표가 서로 모순되는 결과를 보임. 워크로드가 초 단위 단기 세션 중심임을 파악하고 **샘플링 기반 측정**(ASH, `sar`, `/proc` 직접 파싱 스크립트)으로 전환.
4. **핵심 단서 포착** — Oracle ON CPU, systemd·dbus·journald, 커널 sys time 등 **성격이 다른 모든 계층에서 소모 비율이 동일하게 1.14~1.24배**로 나타남. 특정 프로세스·SQL 문제라면 국소적으로 나타나야 한다는 점에서 CPU 실행 성능 자체를 의심.
5. **가설 검증** — 명목 클럭(2194MHz)·BogoMIPS가 동일함을 확인한 뒤 `openssl speed`로 순수 연산 처리량 측정. 12개 측정 구간 전부에서 평균 12% 열세를 실측.
6. **조치 및 검증** — 가상화 담당으로서 Prism에서 해당 VM이 CPU 사용률 80% 노드에 배치된 것을 확인, 여유 노드로 라이브 마이그레이션. 이관 후 벤치마크가 상대 서버와 동등 수준으로 회복됨을 재측정으로 확인.

**결과**

- CPU 사용률 71.3% → 59.0% (주간 동일 시간대 기준, 12.3%p 감소)
- 서버 간 사용률 비율 1.15 → 0.92로 역전, 이상 현상 해소
- 조사 과정에서 **실행당 2.8GB를 스캔해 1건 미만을 반환**하는 SQL을 발견(DB CPU의 약 20% 점유). 정량 근거와 함께 AP 담당 조직에 개선 요청 전달

**배제 항목** (근거 데이터와 함께 문서화)  
실행계획 변경, 바인드 민감도, 결과 건수, THP, 커널 파라미터 드리프트, TCP 파라미터, HugePages, cgroup 귀속, journald 부하, SSH 세션 수, 파스 에러, 컨텍스트 스위치

**사용 도구**  
AWR (`DBA_HIST_OSSTAT` / `SQLSTAT` / `ACTIVE_SESS_HISTORY` / `SYS_TIME_MODEL`), ASH, DBMS_XPLAN, sar·pidstat, vmstat, systemd-cgtop, journalctl, `/proc` 파싱 스크립트, openssl speed

### C. 면접 구두 설명용

> 동일한 SQL이 두 서버에서 CPU를 다르게 쓰는 현상이었습니다. 처음엔 DB 문제로 보고 실행계획부터 봤는데 전부 동일했고, OS로 내려가서 THP나 커널 파라미터 차이도 잡아봤지만 개선이 없었습니다.
> 
> 전환점은 지표를 계층별로 나열했을 때였습니다. Oracle도, systemd도, 커널 sys time도 전부 정확히 1.2배씩 높았습니다. 특정 소프트웨어가 원인이라면 그 계층만 튀어야 하는데 전 구간이 균일하다는 건 CPU 자체가 느리다는 뜻이라고 판단했습니다.
> 
> 클럭은 같았기 때문에 openssl 벤치마크로 실제 연산 처리량을 재봤고, 12% 차이가 실측으로 나왔습니다. 가상화 담당이기도 해서 Prism에서 확인해보니 해당 VM이 사용률 80% 노드에 있었고, 여유 노드로 옮긴 뒤 벤치마크와 실사용률이 모두 정상화됐습니다.
> 
> 이 건에서 배운 건 **가설을 배제하는 것도 진전**이라는 점입니다. THP나 커널 파라미터를 튜닝했을 때 효과가 없었던 것이 결국 "소프트웨어가 아니다"라는 방향 전환의 근거가 됐습니다.

### 활용 시 참고

**기존 소재와 대비를 만드시면 좋습니다.** 이미 준비하신 WAS 스왑 건은 sar로 THP를 특정해 **소프트웨어 튜닝으로 증설 없이 해결**한 사례인데, 이번 건은 THP를 포함한 소프트웨어 가설을 전부 배제하고 **인프라 배치가 원인**임을 밝힌 정반대 케이스입니다. 두 개를 나란히 두면 "지표를 보고 판단하지 선입견으로 접근하지 않는다"는 메시지가 강해집니다.

**포스트모템 질문 대비에도 맞습니다.** 패스오더 면접에서 장애 회고 질문이 많이 나왔다고 하셨는데, 이 건은 가설-측정-배제 사이클과 배제 근거 문서화가 전부 남아 있어서 회고 사례로 쓰기 좋습니다.
